## 1. Best practices & code quality

### Q-1 (P0): The push count was wrong twice over — and the collapse made it unfixable by editing

`scripts/update_activity.py` (old) rendered pushes as:

```python
commits = payload.get("commits", [])
count = len(commits)
```

The Events API omits `payload.commits` for these pushes, so every push
rendered “Pushed 0 commits”. That is the bug behind the live lines.

The second half is subtler and is why a naive fix (“just use
`payload.size`”) would not have been enough. `build_activity_lines`
appended the first push's rendered line, then, when a later push to the
same repo+branch arrived, mutated the stored event's payload:

```python
seen_repos_for_push[key]["payload"]["commits"] = (
    seen_repos_for_push[key]["payload"].get("commits", []) + payload.get("commits", [])
)
continue
```

The appended line string was never rebuilt, so the accumulated count
never reached the output. Collapse existed in the data structure and
nowhere in the rendered page.

**Fix (applied, `scripts/update_activity.py`):** collapse first,
render second. Pushes to the same repo+branch are summed into
`(event, total)` pairs, then rendered once. The count rule is
`size` → `commits` list → unknown, and unknown renders as no count
(“Pushed to …”), never as 0.

**Live verification, Oct 31, 2026:** all 47 PushEvents on the first
Events API page carried *neither* `size` *nor* `commits`
(keys: `before, head, push_id, ref, repository_id`). So today the
correct output is count-less for every push — which is exactly what
the fixed script produced in its dry run (see §6), and exactly what
the external refresh renderer already produces. A true count would
need one compare-API call per push; §3 (A-8) explains why that is
not worth it. Do not “fix” this by hardcoding a count or by reading
`before`/`head` SHAs — neither is a commit count.

### Q-2 (P1): `re.sub` with an unescaped replacement

The old `update_readme` passed the rendered section as the
replacement argument to `re.sub`. In a replacement, `\1` means “group
1”. An issue or PR title containing a backslash sequence could corrupt
the README or raise. **Fix (applied):** splice by string index —
`content[:start] + new_section + content[end:]` — which copies the
replacement verbatim. Covered by `test_backslash_in_title_survives`.

### Q-3 (P1): Dead exit code

```python
changed = update_readme(lines)
sys.exit(0 if changed else 0)
```

Both branches are 0. **Fix (applied):** `main()` returns real codes —
0 ok, 1 markers missing, 2 bad config or failed fetch — and the
workflow can now distinguish “nothing changed” from “something broke”.

### Q-4 (P1): Unvalidated environment input crashes at import time

`MAX_LINES = int(os.environ.get("MAX_LINES", "5"))` at module level
meant a typo in the workflow produced a `ValueError` traceback with
no hint about which variable was wrong, and made the module
unimportable in tests without setting env vars. **Fix (applied):**
`load_config()` validates and raises a plain message; pure functions
take `username`/`max_lines` as arguments instead of reading module
globals, which is also what makes them unit-testable.

### Q-5 (P1): One page, 50 events, no pagination

The old fetch asked for `per_page=50` and stopped. After filtering
(skipped events, profile-repo events, collapsed pushes), 50 fetched
events could yield far fewer than 5 lines, and the oldest page
boundary was invisible. **Fix (applied):** `per_page=100`, follow the
`Link: rel="next"` header, cap at 3 pages. The dry run fetched 139
events across 2 pages.

### Q-6 (P1): No HTTP error handling

`urlopen` raised raw `HTTPError`/`URLError` into the workflow log.
**Fix (applied):** both are caught and re-raised as `RuntimeError`
with status and, for 403s, the rate-limit reset epoch, and `main()`
maps that to exit 2. Unauthenticated callers get 60 requests/hour;
the workflow already passes `GITHUB_TOKEN`, so this mostly matters
for local runs.

### Q-7 (P1): No tests, and the workflow never exercised the script except in production

The only execution of the script was the twice-daily production run
that rewrites the public profile. **Fix (applied):**
`tests/test_update_activity.py`, 13 stdlib `unittest` cases covering
the count rule, collapse, filtering, `MAX_LINES`, title-less PRs,
marker splicing, the backslash case, and missing markers. The updated
workflow runs them before the script. Run them with
`python3 -m unittest discover -s tests -v`.

### Q-8 (P1): Workflow: unpinned Python, no concurrency guard

`python3` on `ubuntu-latest` drifts with the runner image, and two
overlapping runs (schedule + manual dispatch) could both commit and
push from the same base. **Fix (applied, workflow file in this
review):** `actions/setup-python@v5` pinned to 3.12, a test step
before the run step, and a `concurrency` group
(`profile-readme-activity`, `cancel-in-progress: false` — a run that
already committed must not be killed mid-push). The workflow change
is **unverified until its first run after adoption**: CI here is the
gate, and it has not run yet.

### Q-9 (P1): Fallback titles print lines that say nothing

Live activity shows “Merged PR [a pull request]” and “Opened PR [a
pull request]”. A title-less PR line carries no information and looks
broken. **Fix (applied):** PR, issue, comment, and release events
with a missing title/tag now return `None` (skipped) instead of a
placeholder. Titles are present in practice; the fallback only fired
on malformed payloads. Note the attribution: the live “a pull
request” lines cannot have come from the script in this tree in its
current form — see A-1 — but the fix is right for whichever renderer
owns the section.

### What is already good (keep it)

- Stdlib only. No dependency to pin, audit, or break. Do not add
  `requests` for this script; `urllib` is sufficient and already here.
- Marker-based editing with a hard error when markers are missing,
  instead of silently appending a second section.
- `SKIP_EVENTS` and profile-repo self-skip are the right instincts;
  they just needed the why-comments, which the fixed script now has.
- Workflow permissions are already minimal (`contents: write`).

## 2. Commenting & in-code documentation

The old script had a module docstring and almost nothing else: no
function docstrings, and no explanation for the decisions a future
maintainer will question first — why the profile repo is skipped, why
`[skip ci]` appears on some bot commits, why counts come from `size`,
why markers are a hard error. The fixed script adds Google-style
docstrings to every function and why-comments at exactly those
points, including the Oct 31 live-API observation that both count
fields are currently absent. The pattern to keep: comment the *why*
(the API omits the field; unknown is not zero; re.sub treats
backslashes as escapes), not the *what* (the next line already says
what). `ruff` has no docstring rules configured in this repo, and
adding a linter config for a single script would be more machinery
than the script warrants — the tests are the enforcement here.

## 3. Future-proofing & architecture

### A-1 (P0): Two writers, one file — the root cause of the visible symptoms

Evidence, all from this repo's own history:

- `.github/workflows/update-activity.yml` runs the in-repo script and
  commits as `41898282+github-actions[bot]@users.noreply.github.com`
  (“chore: update README with recent activity”, e.g. `d4947e0`).
- A second process commits as `github-actions[bot]@users.noreply.github.com`
  (no numeric prefix) with “chore: refresh profile data [skip ci]”
  (e.g. `2b53b14`). It rewrites the stats section — and, in that same
  commit, changed an activity line from “Pushed 0 commits to
  [`enonymous1/jpl-dev`]” to “Pushed to [`enonymous1/jpl-dev`]”.
- No second workflow file exists on `main`. The refresh process is
  defined elsewhere (or run locally with a bot-like git identity) and
  is invisible from this repo, which is itself part of the problem.

So the activity section's format flips depending on which writer ran
last, and neither writer's owner can see the other writer's code from
this repo. **Concrete fix, decision required (yours):** assign one
owner per section and enforce it in the code — the activity script
owns `START_SECTION:activity` and must never touch stats; the refresh
owns `START_SECTION:stats` and must never touch activity — then
delete the losing writer's activity code. The rewritten README draft
documents this ownership explicitly so the next person does not
reintroduce the second writer by accident. Until that decision is
made, do not “fix” the activity format in one writer and expect it to
stick: the other writer will revert it on its next run, as `2b53b14`
did to `d4947e0`.

### A-2 (P1): `header.gif` is a binary with no source in the repo

The 128 KB header was generated by a Pillow script that lived outside
the repo. Nobody can regenerate, tweak, or review it from the repo
alone. **Fix (applied):** `scripts/build_header.py` (the actual
generator, with its output path made repo-relative) is included in
this review. Commit it alongside the GIF; the draft README documents
the regenerate-and-commit-the-GIF rule.

### A-3 (P2): Dead `output` branch

The snake workflow file is gone from `main`, but `origin/output`
still exists. Nothing references it anymore. Proposed cleanup, after
confirming nothing else points at it:

```powershell
git push origin --delete output
```

### A-4 (P1): No LICENSE

A public repo containing code (the updater, the header generator)
with no license file leaves reuse terms undefined. Every other
portfolio repo of yours ships MIT. This review does not pick the
license for you — that is your call — but the gap should be closed
deliberately, not left: add `LICENSE` (MIT, Copyright 2026 Justin
Lyons, if you choose MIT) and a `license` note in the README draft's
Description. See §7.

### A-5: Configuration is mostly right

`GH_USERNAME`, `TARGET_FILE`, `MAX_LINES`, and `GITHUB_TOKEN` are
already env-driven, and the `enonymous1` default is correct for a
repo whose entire purpose is one profile. The hardcoded values that
*should* stay hardcoded are the cron schedule and the bot identity
(they describe this repo's automation, not a deployment variable).
Do not generalize this script into a multi-user tool; that is what
profileforge is for, and a second general-purpose activity updater
would recreate the A-1 problem in a new form.

### A-6: Third-party badge hosts are single points of failure

The README depends on seven external hosts (typing SVG, skillicons,
shields, komarev counter, capsule-render footer, git.io, LinkedIn).
If any is down, that section degrades or breaks, with no fallback
beyond `alt` text — and several badge images have no meaningful
`alt`. This is accepted risk for a profile page (the alternative is
a plainer page), but two cheap improvements: keep the stats and
activity sections first-party (already done — do not reintroduce
third-party stat cards), and do not add new third-party images
without an `alt` that still reads sensibly when the image fails.

### A-7: The stats section's ownership was undocumented

Before this review, nothing in the repo said who writes the stats
section, what method it uses, or that hand edits inside the markers
are overwritten. The draft README's Description and Local Development
sections now say all three. The stats method itself (Languages API
vs. clone audit) is a refresh-process concern, not something this
repo can verify; the draft points at this review for the Oct 29
clone-audit cross-check rather than restating numbers that will rot.

### A-8 (proposed, not applied): Commit-count enrichment via the compare API

If real push counts ever matter enough to justify the cost, the
honest way is one compare call per push (`/compare/{before}...{head}`)
behind an opt-in flag, with its own quota budget and a fallback to
count-less rendering when the budget runs out. Not implemented:
today's live payloads carry no count at all, the count-less line is
correct, and 5 profile lines do not justify up to 5 extra API calls
per run. Revisit only if you decide counts are load-bearing.
